# Чеклист симптомов для проверки value case

Это не строгие правила, а симптомы, на которые стоит обратить внимание при валидации value case.
Решение о правке принимается в контексте конкретной модели.

---

## Название

### Название теряет смысл при замене тире на "хочет"

Название "Актор — действие" должно выдерживать замену тире на "хочет". Если после замены фраза теряет смысл или звучит неестественно — название построено неправильно.

**Было:** "Автор — опубликовать курс" (замена: "Автор хочет опубликовать курс" — смысл сохранён, нормально)

**Было:** "Ревьюер — принятая работа" (замена: "Ревьюер хочет принятая работа" — смысл потерян, симптом)

**Как исправить:** в правой части должно быть действие (глагол), а не состояние. "Принятая работа" → "Принять работу". После замены на "хочет" фраза должна читаться осмысленно.

---

## Обстоятельства

### Обстоятельство пересказывает название

Обстоятельство должно уточнять контекст, а не повторять заголовок. Если из названия уже ясно, что делает актор, — в обстоятельствах нужно писать, при каких условиях он это делает.

**Было:** Название "Автор — опубликовать курс", обстоятельство "автор хочет опубликовать курс"

**Стало:** "Черновик курса готов"

**Как исправить:** убрать дублирование. Оставить только то, что не очевидно из названия.

### Обстоятельство описывает требование или желание

Обстоятельства описывают контекст — фактические условия, в которых находится актор. Если вместо факта написано требование или желание ("должен", "обязан", "хочет", "желает", "надо"), то это ограничение, которое может быть лишним или неотносимым к сценарию.

**Было:** "Курс должен быть открыт"

**Стало:** "Открытый курс"

**Как исправить:** переформулировать требование как факт. "Должен быть X" → "X".

### Обстоятельств больше 3–4

Сценарий перегружен деталями, теряется фокус. Критических обстоятельств обычно 1–2, редко 3.

**Было:** "Урок не начат, ученик записан, курс опубликован, нет долгов, интернет работает, время не позднее 23:00"

**Стало:** "Ученик записан на курс, урок не начат"

**Как исправить:** оставить только те обстоятельства, без которых сценарий теряет смысл. Остальное — шум.

---

## Результаты

### Название результата описывает процесс, а не результат

Результат — это описание состояния, а не процесса. Его используют как ссылку из других мест модели.

**Было:** "Курс создан как черновик"

**Стало:** "Черновой курс"

**Было:** "Ревьюер назначен на курс"

**Стало:** "Назначенный на курс ревьюер"

**Как исправить:** название результата = "какой" + концепт.

### Акцептор описывает действие вне зоны видимости актора

Акцептор — то, что актор сам видит или получает. Нельзя писать акцепторы от лица другого участника.

**Было:** в сценарии ревьюера акцептор "ученику отправлено уведомление"

**Стало:** только то, что видит или может проверить ревьюер

**Как исправить:** проверять каждый акцептор вопросом "актор этой роли может это увидеть / подтвердить?"

### В результате value case написано то, что случится после value case или уже случилось до него

Результат — новое состояние актора после сценария, а не действие, совершённое кем-то другим.

**Было:** "Работа принята" (в сценарии ученика)

**Стало:** "Знание того, что работа принята"

**Как исправить:** если результат можно переписать от первого лица ("я узнал, что...") — это правильная формулировка.

### У результата больше 3–4 акцепторов

Результат слишком раздутый, смешиваются разные исходы.

**Было:** один результат с 6 акцепторами

**Стало:** два результата по 2–3 акцептора

**Как исправить:** если акцепторы описывают принципиально разные исходы — разбить на несколько результатов. Если это просто детали одного исхода — оставить, но проверить, не избыточно ли.

## Делегирование (что понадобится)

### Делегируется концепту, которого нет в модели

Если в "что понадобится" указана сущность, которой нет в концептах, — модель неполна или делегирование идёт в никуда.

**Было:** описан только концепт "Веб-сервис", при этом в value case такое делегирование: "Сервис отправки уведомлений - Отправить уведомление по SMS"

**Стало:** "Веб-сервис - Отправить уведомление по SMS."

**Как исправить:** либо добавить концепт, либо заменить на существующий.

### Делегирование описано объективно, не от лица актора

Формулировка должна отвечать на вопрос "что актор получит от системы", а не "что система сделает".

**Было:** "Веб-сервис - Уведомить ученика"

**Стало:** "Веб-сервис - Увидеть уведомление"

**Было:** "Ревьюер - Проверить код"

**Стало:** "Ревьюер - Увидеть результат проверки кода"

**Как исправить:** переформулировать со стороны актора: что он увидит, получит, сможет сделать в результате делегирования.

### Делегирована работа, которая не поможет актору в его value case

В "что понадобится" попадают действия, которые нужны системе, а не актору. Это раздувает сценарий.

**Было:** "Ученик - показать работу ревьюеру".

**Как исправить:** проверять, что каждое делегированное действие нужно именно этому актору для достижения его цели.

### Концепту делегировано действие, которое он не может выполнить

Веб-сервис, система или другой концепт наделяется функцией, которая ему не свойственна.

**Было:** "Веб-сервис — проверить работу"

**Стало:** "Веб-сервис — отправить работу на проверку"

**Как исправить:** проверить, что концепт действительно может выполнить это действие в рамках модели. Если нет — разбить на шаги или сменить концепт.

---

## Композиция и декомпозиция

### Несколько value cases можно объединить без потери смысла

Если у нескольких value cases один актор, похожие обстоятельства и результаты — их можно объединить в один с несколькими результатами.

**Было:** 4 value case ("увидеть работу", "взять работу на проверку", "принять работу", "вернуть на работку")

**Стало:** 1 value case с 2 результатами (принять работу, вернуть на доработку) и 2 обстоятельствами ("вижу работу", "взял работу на проверку").

**Как исправить:** объединить, если все кейсы — это вариации одного сценария с разными исходами.
