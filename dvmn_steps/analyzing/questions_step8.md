# Уточняющие вопросы по контракт-паку (step 8)

## 1. Пользователи
В карточках концептов нет сущности «Пользователь/Ученик/Преподаватель». В схеме student_id — внешний UUID без FK. Нужна ли таблица users с ролью (student, teacher, admin)?

**Решение:** Добавить таблицу `users` с полями `id`, `student_id`, `role` (enum: student, teacher, admin), `name`, `email`. Это обеспечит FK-связи для всех `student_id` и `reviewer_id`, устранит «висячие» UUID и позволит корректно работать REFERENCE в vmap.

## 2. Ревью
Есть поле reviewer_comment в student_works, но нет отдельной сущности «Ревью». Нужна ли таблица reviews с историей проверок (reviewee, reviewer, verdict, комментарии)?

**Решение:** Добавить таблицу `reviews` с полями `id`, `student_work_id`, `reviewer_id` (FK → users.id), `verdict` (approved, changes_requested), `comment`, `created_at`. Это позволит хранить историю проверок, поддерживать повторные ревью и аудит.

## 3. Прогресс по шагам
student_progresses фиксирует только текущий урок. Нужна ли таблица step_completions для отслеживания, какие шаги ученик прошёл?

**Решение:** Добавить таблицу `step_completions` с полями `student_id`, `step_id`, `completed_at` (составной PK). Это даст точную аналитику по каждому шагу и позволит восстановить прогресс ученика после сбоя.

## 4. Группы и расписание
У groups нет полей для расписания/дат доступа. Нужны ли они, или группа — только логический ярлык для разграничения видимости курса?

**Решение:** Группа — логический ярлык для разграничения видимости курса. Даты доступа задавать на уровне курса или урока через поля `available_from` / `available_until`. Добавлять расписание в groups избыточно.

## 5. Дедлайны уроков
У lessons есть deadline и deadline_type. Дедлайн — один на урок. Нужна ли поддержка разных дедлайнов для разных групп учеников внутри одного курса?

**Решение:** Добавить таблицу `lesson_group_deadlines` с полями `lesson_id`, `group_id`, `deadline`, `deadline_type`. Один урок сможет иметь разные дедлайны для разных учебных потоков, а `lessons.deadline` будет значением по умолчанию.

## 6. Автор курса
В карточках упоминается «автор», но нет поля author_id. Нужна ли связь курса с пользователем-автором?

**Решение:** Добавить поле `author_id` (FK → users.id) в таблицу `courses`. Это необходимо для разграничения прав: автор (и админ) могут редактировать курс, остальные — только читать.

## 7. Категории работ
В концепте «Работа ученика» перечислены 9 категорий (на ревью, проверенная, принятая, на доработке, просроченная, черновик, тест, интерактивная, кодирование). В схеме status покрывает только 5 состояний жизненного цикла, а тип работы (тест/кодирование/интерактив) не моделируется. Нужно ли поле work_type?

**Решение:** Добавить поле `work_type` (enum: test, coding, interactive). `status` описывает жизненный цикл (draft, submitted, approved и т.д.), `work_type` — природу задания. Это два независимых измерения, и оба необходимы для корректного моделирования предметной области.
