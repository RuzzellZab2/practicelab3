# Отчёт: смысловые ошибки в концептах

Проверка карточек концептов (`concepts/`) на внутренние противоречия, несостыковки ролей и ошибки классификации.

## 1. Противоречие: кто публикует курс — автор или администратор

- `concepts/course.md:31-33` («Опубликованный курс») — «курс, который **опубликован Администратором**», пример про «запрос Администратору на публикацию… одобрение Администратором».
- `concepts/course_author.md:7` — автор «**публикует свои курсы**», и есть value case «Автор курса — опубликовать курс» (`course_author.md:101`).

Поток «автор → запрос → одобрение администратором» отсутствует в value cases, а PoC реализует публикацию автором. Карточка `course.md` описывает несуществующий сценарий.

## 2. Противоречие: кто назначает ревьюера — автор или администратор

Прямое противоречие даже внутри одного файла:

- `concepts/course_author.md:7` — автор «назначает на курс проверяющего»; value case «Автор курса — назначить ревьюера на курс» (`course_author.md:115`).
- `concepts/course_author.md:24` — «администратор — за доступ: … **назначение ревьюеров**».
- `concepts/user.md:43` («Администратор») — «…**назначает ревьюеров**».
- `concepts/reviewer.md:34` («Ревьюер урока») — «**администратор** назначил Марию ревьюером».

## 3. Противоречие в уровне дедлайна: курс или урок

- `concepts/course.md:37` — «**Курс** с дедлайном».
- `concepts/lesson.md:35` — «**Урок** с дедлайном».
- value case — только «Автор курса — установить **дедлайн урока**» (`course_author.md:86`); дедлайна курса в сценариях нет.
- `concepts/group.md:33` — «дедлайны настраиваются на уровне **курса или урока**».

Модель не определяет, на каком уровне живёт дедлайн.

## 4. Ошибка категоризации: «Практическая работа» — категория, дублирующая сам концепт

`concepts/student_work.md`:

- «Практическая работа» указана в **Синонимах** (`:14`), то есть это и есть «Работа ученика».
- Одновременно заведена как **категория** (`:46-48`) с определением «работа, которая отправляется на проверку ревьюеру» — почти дословно совпадает с категорией «Работа на ревью» (`:34-35`).

Категория должна добавлять различающий признак, а не повторять сам концепт и не пересекаться с другой категорией.

## 5. Терминологический разнобой «оценка» vs «вердикт»

- `concepts/course.md:38` — «ревьюер не может **поставить оценку**».
- `concepts/course.md:39` (пример той же категории) — «ревьюер не может **вынести вердикт**».

В модели нет понятия «оценка» — только «вердикт (принято / на доработку)».

## 6. Терминологический разнобой «проверяющий» vs «ревьюер»

- `concepts/course_author.md:7` — «назначает **проверяющего**».
- `concepts/course_author.md:107` (обстоятельство «опубликовать курс») — «**проверяющий** курса назначен».
- При этом роль называется «Ревьюер», и value case — «назначить **ревьюера**».

## 7. «Черновик ревью» vs «черновик комментария»

- `concepts/review.md:34-36` — категория «**Черновик ревью**» («неоконченный комментарий ревьюера»).
- `concepts/reviewer.md:62` (value case «проверить работу») — «увидеть сохраненный **черновик комментария**».

Одно и то же явление названо по-разному.

## 8. Мелкие замечания

- `concepts/user.md:43` — «открывает доступ к курсам, **группами, пользователями**» — несогласованные падежи (должно быть «к группам, к пользователям»).
- `concepts/group.md:33` — ссылка на техническое поле `lesson_group_deadlines` — утечка реализации в карточку концепта (нарушение рамки «без реализации»).
- `concepts/student.md:8` — «роль Ученик присваивается всем при регистрации», но `student.md:19` / `reviewer.md:17` говорят, что роли контекстные («учеником в одном курсе, ревьюером в другом»).
